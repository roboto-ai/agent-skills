# Upload agent configuration rules

Each rule below names either a failure mode that keeps data from reaching Roboto or one that destroys it on the way. Apply every rule that bears on the deployment; cite the rule number when a requirement forced a choice.

Every behavior below was checked against the `roboto/upload_agent/` source in the SDK release recorded as `verified-sdk` in the `metadata` block of `SKILL.md`, and by parsing configs, writing auto-created markers, matching patterns, and holding the lock locally with that release through `uv run --with roboto python -c ...`, on the date recorded as `verified-on`. Device attribution was checked against the devices page of the Roboto docs (www.roboto.ai/docs), and the API scopes of each call against the REST API reference there. A newer release can change any of it: re-check what you use against source 1 of SKILL.md's "Sources, in order of authority". Where this file and a live source disagree, the live source wins.

## The two files

1. **Keep machine settings in the agent config and dataset settings in the marker, and parse both after writing them.** The agent config (`~/.roboto/upload_agent.json`) says where to look and whether to delete; the marker says what one dataset is. Neither model rejects unknown keys, so tags put in the agent config, a search path put in a marker, or a misspelled key is dropped without a log line, and the run uses the default. Parse each file with its model and compare the output with what you wrote (SKILL.md Phase 2).

2. **Do not rely on a marker's `name`, `device_id`, or `custom_fields`.** The marker model accepts them because it extends the dataset-creation request, but the agent creates the dataset with only the description, metadata, tags, and org. A dataset gets its device from a device credential (rule 8); a name or custom fields need a step after upload, such as `roboto datasets update -d <ds_id> --name <name>`.

3. **Configure the agent as the user it will run as.** The agent config, the marker template (`default_roboto_upload.json`), and the lock (`tmp/upload_agent.lock`) all live in `~/.roboto/` of the user running the agent. `ROBOTO_CONFIG_FILE` moves only the credentials file. A config written as one user and a service running as another finds no config and uploads nothing.

## Scanning and markers

4. **Treat the completion file as the agent's record of an upload.** On success the agent deletes the marker and writes `.roboto_upload_complete.json` naming the dataset. Discovery looks for markers, so the directory is no longer found; a restored marker is still skipped while a completion file exists, even an unparseable one (the warning for that case names the in-progress file's path, not the completion file's). Forcing a re-upload takes both steps: delete the completion file and restore the marker. The next pass then creates a new dataset; to upload into the same dataset instead, also write an in-progress file naming it (format in `references/agent-api.md`).

5. **Never let the agent see a directory that is still being written.** It uploads what exists at that moment, deletes the marker, and writes the completion file, so files that arrive later are never uploaded. Have whatever ends a recording write the marker as its last act, so the marker means "this recording is finished". Where that is impossible, keep recordings outside the search paths until they are complete. With `run -a`, a directory is eligible as soon as it is non-empty, so auto-creation alone does not satisfy this rule.

6. **Use auto-creation only for recordings exactly one level below a search path.** `run -a` considers only the direct subdirectories of each search path. It skips empty ones and ones that already hold a marker, an in-progress file, or a completion file. In a layout that nests recordings two levels down, such as `<search path>/<robot>/<date>/`, it writes the marker into `<robot>/`, so every recording under it so far becomes one dataset. That directory then holds a completion file, so `-a` never marks it again, and recordings added under it later are never uploaded.

7. **Check every variable a marker template uses in the service's environment.** When the agent auto-creates markers, it replaces `$NAME` and `${NAME}` in the template with that environment variable's value. An unset variable becomes an empty string with no warning, and so does a literal `$` followed by letters or digits, such as `$5`. The `$NAME` form is replaced as plain text, so a variable whose name begins another's corrupts it: with `$USER` earlier in the template, `$USERNAME` becomes the user's name followed by `NAME`. Write every variable as `${NAME}`, which this cannot happen to. A template that does not parse, before or after substitution, logs one WARNING and is replaced by the blank marker, which the agent writes into each eligible directory: those datasets get no description, tags, or metadata, and no `org_id` (rule 9). Under a service manager the environment is the unit's, not the interactive shell's: set the variables in the unit, and confirm their values in the first dataset's metadata.

## Identity and org

8. **Run the agent on a device credential when datasets must be attributed to the machine.** The agent never sends a device ID. When it runs on a device's token, Roboto attributes each dataset it creates to that device. On a personal token, datasets arrive without a device; fixing that is a step after upload (`roboto datasets update -d <ds_id> --device-id <device_id>`).

9. **Give the agent its org explicitly unless it runs on a device credential.** A device credential is bound to its org. A personal token for a user in more than one org needs `org_id` in every marker, or `default_org_id` in merge mode; otherwise dataset creation raises `RobotoNoOrgProvidedException` and the pass ends (rule 15). The agent does not read `ROBOTO_ORG_ID` or the profile `org_id` that `roboto setup` saves, so a CLI that works without `--org` does not prove the agent has an org.

10. **Check collection membership as part of verification.** The agent adds a dataset to the marker's collections after the upload; a failure is logged at ERROR and does not fail the upload, so the data arrives and the collection does not change. The collection must hold datasets: `roboto collections create` without `--resource-type dataset` or `--dataset-id` makes a file collection, which refuses every add.

11. **Use merge mode only when every marker carries the same properties.** `run -m` creates one dataset in each pass that finds markers, in `default_org_id`, and applies each marker's description, metadata, and tags as successive updates in an order that is not fixed, so a conflicting value is whichever marker came last. Collection additions are skipped in merge mode, with no log line. Each directory's files keep paths relative to their own marker's directory, so two directories that each hold a file of the same name write the same dataset path, and the later upload replaces the earlier one there.

## Deletion

12. **Enable deletion only after a verified round trip, on the user's explicit word, and test it on data the user can lose.** On a robot the local copy is often the only copy. The agent deletes a directory's uploaded files after all of them are uploaded, by its own measure of success; directories stay. `--yolo` never resolves this decision. Confirm the dataset is complete in Roboto before confirming the files are gone.

13. **Expect empty-directory cleanup to skip any recording with subdirectories.** The agent removes a directory only when it is empty or holds nothing but the completion file. Deletion removes files, not subdirectories, so a recording with any subdirectory keeps them, empty, and is never removed. A file the patterns excluded stays too.

## Operation

14. **Make credentials non-interactive, readable by the service user, and renewed before they expire.** A credential exported in an interactive shell profile works during setup and is missing under a service manager. The agent reads its credentials once per process, so restart it after renewing a token. Record the expiry date in `SPEC.md`; `references/agent-api.md` lists each kind's lifetime. A device token from `roboto devices register` carries no API scopes, so it is not restricted. A token restricted to `ApiScope.minimal_uploader()` can create datasets and upload files, but the REST API reference lists `api.everything_else` for the agent's other calls: reading the dataset named in an in-progress file (`GET /v1/datasets/{dataset_id}`), adding to a collection (`PUT /v1/collections/id/{collection_id}`), and the dataset updates of merge mode (`PUT /v1/datasets/{dataset_id}`). Without it, a resumed upload ends the pass (rule 15) and a collection add fails (rule 10).

15. **Run the agent under a restart policy, and read its log when uploads stop.** Any exception in a pass ends the pass, and `run --forever` exits with it. A network outage, a missing org, or an in-progress file naming a dataset that no longer exists all do this. The failed marker is still there on the next pass, so the same error repeats, and markers the scan reaches after it do not upload until someone fixes the cause.

16. **Know what the lock message means.** The agent takes `~/.roboto/tmp/upload_agent.lock` with a 1-second timeout. A second run finds it held, logs at INFO that the agent appears to be running already and that the lock may be orphaned, and exits without uploading. That makes overlapping runs harmless. The lock is an operating-system file lock: the system releases it when the process holding it exits, and the lock file left on disk does not block later runs. So when every run logs this message, another agent process is still running, such as a hung upload or a second service; find it with `fuser -v ~/.roboto/tmp/upload_agent.lock` or `lsof` and stop it. Deleting the file does not stop that process, and lets a new run start beside it. (On a filesystem without `flock` support, such as some network mounts, the lock library falls back to treating the file's existence as the lock, and a file left behind does block every run.) A lock file the agent's user cannot open, such as one another user created, ends every run with a `PermissionError` traceback instead of the message; fix its owner. `-q` or a single `-v` hides the message. Put the lock path, the message, and this check in the runbook.

## Content

17. **Write upload patterns against file names, not paths.** The agent matches `include_patterns` and `exclude_patterns` against each file's name. `*.log` and `**/*.log` work; `camera/**` and `logs/*.log` match nothing, so an exclude like that uploads the directory anyway and an include like that uploads nothing. To leave out a subdirectory, keep it outside the recording directory.

18. **Never nest one marker's directory inside another's.** The agent finds every marker in the tree. The outer marker uploads the whole tree, including the inner directory, and the inner marker uploads its directory again into a second dataset.

19. **Never put a secret in a marker or template.** The marker sits in the directory being uploaded and is uploaded with it unless the patterns exclude it.
