# Upload agent configuration rules

Each rule names either a failure mode that keeps data from reaching Roboto, or one that destroys it on the way. Cite the rule number when a requirement forced a choice.

## The two files

1. **Two config files, two scopes. Do not conflate them.** The **agent config** is one per machine and says where to look: the directories to scan, the marker filename to look for, and the machine-wide deletion settings. The **per-directory marker** is one per recording, and its presence is what marks a directory as a dataset to upload; it carries that dataset's own name, description, metadata, tags, device id, collections, and per-directory include and exclude patterns. Putting a dataset's tags in the agent config, or a search path in a marker, silently does nothing: neither model rejects unknown keys, so the field is dropped and the run proceeds on defaults with nothing in the log. **A field in the right file can also be ignored** — the marker's model accepts a dataset name and a device id, and the agent passes neither when it creates the dataset. Datasets the agent uploads arrive unnamed and unattributed; apply both after the fact if they are needed.

2. **The completion marker is the agent's memory — and the upload marker is its eyes.** On success the agent writes a completion file naming the dataset the data went to, **and deletes the upload marker**. Discovery scans for markers, so a completed directory is not skipped on sight; it is no longer seen at all. Forcing a re-upload therefore takes two steps: delete the completion file *and* restore the marker. Deleting only the completion file does nothing. If a marker is restored while the completion file remains, the directory is skipped on sight — and a completion file that cannot be parsed is still treated as a reason to skip, deliberately, so a corrupted one looks exactly like a finished upload.

## Deletion — the rules that destroy data

3. **Deleting uploaded files removes the local copy, and on a robot that is often the only copy.** The agent deletes after its own notion of a successful upload. Never enable it before a full round trip has been verified against the live platform, never enable it without the user's explicit word — including under `--yolo` — and verify it separately, on data the user can afford to lose. Confirm the dataset is complete in Roboto **before** confirming the files are gone locally; the other order teaches you nothing you want to learn that way.

4. **Empty-directory cleanup is narrower than it sounds, and is still deletion.** A directory is removed only when it is empty or holds nothing but the completion marker; anything else left behind stops it. That makes it safe against surprises and also means it will quietly not fire whenever a stray file remains, which is a support question waiting to happen. It is most useful paired with file deletion, and inherits every caution in rule 3.

## Scanning and markers

5. **An in-progress marker means resume, not restart.** A directory carrying one is picked up again and uploaded into the dataset that marker names, rather than into a new one. This is what makes an interrupted upload safe, and it is worth testing deliberately (SKILL.md Phase 3 step 7) rather than discovering during an outage. Deleting an in-progress marker by hand orphans its dataset and causes the next run to create a second one.

6. **Auto-creation of markers looks exactly one level under each search path.** Directories nested more deeply are not considered, and neither is the search path itself. A layout that nests recordings two levels down gets no markers and uploads nothing, with a log that reports finding no markers rather than an error. Check the depth of the real layout against this before relying on auto-creation.

7. **Never let the agent see a directory that is still being written.** It will upload what exists at that moment and write a completion marker, and that marker means it will never revisit the directory. The reliable pattern is for whatever ends a recording to write the marker as its last act — which makes the marker mean "this recording is finished" rather than "this directory exists". Where that is impossible, the search paths must exclude the directory a recording is written into until it is done.

8. **The concurrency lock makes a second instance a silent no-op — and an orphaned lock stops everything just as silently.** Overlapping runs are harmless by design: the second exits without uploading, so a scheduler firing during a long upload is fine. The cost is that a lock left behind by a killed process makes every subsequent run do nothing while logging that the agent appears to already be running. This belongs in the runbook, because it presents as "uploads just stopped" with no error anywhere.

## Credentials and operation

9. **Credentials must be non-interactive, readable by the service user, and durable across a reboot.** The agent resolves an API key or bearer token from the environment when one is set, and otherwise falls back to a profile in the SDK's config file — either source is fine, and the config file is often the more reboot-durable of the two. What fails is a credential exported in an interactive shell profile: it works during setup and is absent under a service manager, which is the single most common reason an agent that worked yesterday is not running today. Put it where the unit can see it, or set it in the unit. Credentials resolve once per process, so under continuous mode a rotated key needs a restart. Record the expiry in the spec.

10. **Merge mode resolves collisions last-write-wins, in a non-deterministic order — and it is the only consumer of the config's default org.** The machine-wide default org is used solely for the dataset merge mode creates; every per-directory upload takes its org from the marker and never falls back to it, so a multi-org user not using merge mode must set the org in every marker or in the auto-creation template. Merging every upload into one dataset applies each marker's dataset properties as sequential updates, so two markers with different descriptions, or different values for the same metadata key, produce whichever the traversal happened to reach last. Do not use merge mode where the dataset's properties matter; use it where the grouping matters and the properties are uniform.

11. **Environment variables interpolate in the default marker template — and an unset one becomes empty, not an error.** The template used for auto-created markers resolves environment variable references, which is how a fleet distinguishes machines without a per-machine config file: a hostname, a robot id, or a software version lands in dataset metadata that way. The values come from the environment the agent runs in, which under a service manager is not the user's interactive environment — and an unset variable substitutes the empty string, so the metadata key exists carrying nothing. That is the failure mode to check for, since it looks like success.

12. **Never put a secret in a marker file.** It lives on the machine's disk, inside the directory being uploaded, and it is uploaded along with everything else unless excluded. It is for identifying and describing a dataset, not for credentials.

13. **Collection membership is best-effort, and inert under merge mode.** A marker can ask for its dataset to be added to collections; a failure there is logged and does not fail the upload, so the data arrives and the curation silently does not. Under merge mode it is worse than best-effort: the merged dataset never reaches the collection-add path at all, so every marker's request is skipped with no error line whatsoever. Check collection membership as part of verifying the round trip, and add the merged dataset to its collections separately.

## Delivery

14. **Verify before automating, and verify on the machine that will run it.** A configuration proven by one manual run, one repeat run, and one interrupted run is a configuration a service manager can be trusted with. One that has never uploaded anything is a hypothesis about paths that may not exist on that host. Deliver both config files, the service unit, and the runbook as a directory under version control rather than as edits made in place, so the next machine is a copy rather than a re-derivation.
